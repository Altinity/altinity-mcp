02 / thesis

A database-defined application, not just a SQL chatbot.

Use the host as the interface and agent runtime; give it narrow, meaningful application capabilities.

DATA

Read and write

  • Parameterized views: named, typed read operations with discoverable input/output contracts.
  • Append-oriented command tables: low-frequency domain-specific writes where the storage guarantees suffice.
  • DEFAULT expressions and materialized views: generated fields, projections and derived events.
EXPERTISE

Resources and workflows

  • One physical catalog can store documents, instructions, SKILL.md, UI assets and prompt definitions.
  • Skills supply agent expertise; Prompts provide user-selected workflow entry points.
  • Expose contextual documents and citations, not the entire database.
EXPERIENCE

UI and reactions

  • HTML/CSS/JS components from ClickHouse via MCP Apps.
  • MCP Events wake a subscribed agent on important changes.
  • Tasks and Elicitation extend jobs and decisions when the host supports them.
Boundary

No app-specific persistent state or business rules in Go. Generic protocol code, identity infrastructure, delivery workers and browser-side interaction still exist. Clients choose when to call tools; the server and database enforce permissions. Use a transactional dependency where the application's consistency requirements demand it.

07 / build the data model

1. Store domain state and commands.

Example: a low-frequency, single-tenant append-only incident investigation journal. High-volume telemetry arrives in batches; use transactional storage for strict operational workflows.

SQL
CREATE DATABASE IF NOT EXISTS app;

CREATE TABLE app.open_incident
(
    request_id UUID,
    title String,
    severity String,
    incident_id UUID DEFAULT generateUUIDv7(),
    opened_at DateTime64(3) DEFAULT now64(3),
    CONSTRAINT valid_severity
        CHECK severity IN ('critical', 'high', 'normal')
)
ENGINE = MergeTree
ORDER BY (opened_at, incident_id)
COMMENT 'Open an incident';
DESIGN

Use commands, not arbitrary SQL

  • A request has a domain meaning; only required columns are exposed to the agent.
  • Database-generated IDs and timestamps are omitted from tool inputs.
  • Add append-only note and resolution command tables; project a current incident view from the journal.
  • Use constraints, roles and controlled views/MVs to enforce the supported invariants.
Production assumption

Frequent single-row inserts create part and merge overhead; async batching can help. MergeTree ORDER BY is not a unique constraint; request_id is a correlation key, not an exactly-once guarantee. Validate idempotency and concurrency separately; if strict cross-row transactional invariants are mandatory, use a transactional subsystem rather than promise SQL-only correctness.

08 / read tools

2. Publish typed read operations as views.

Business queries stay in ClickHouse; the connector discovers typed inputs and executes with the caller's credentials.

SQL
CREATE VIEW app.list_incidents
SQL SECURITY INVOKER
AS
SELECT incident_id, title, severity, opened_at
FROM app.open_incident
WHERE severity = {severity:String}
ORDER BY opened_at DESC
LIMIT 100;

-- Example invocation in ClickHouse:
SELECT *
FROM app.list_incidents(severity='critical');
YAML
# Existing Altinity MCP configuration:
server:
  tools:
    - type: read
      name: list_incidents
      view_regexp: '^app\.list_incidents$'
    - type: write
      name: open_incident
      table_regexp: '^app\.open_incident$'
      mode: insert
Expose only the application API

In a plugin deployment configure only intended read/write rules; omit raw execute_query and write_query unless the product is explicitly a SQL workbench. Use least-privilege credentials even when a tool is hidden. The example targets one exact view and table; test tool names and schemas via tools/list.

09 / write tools

3. Return real application outcomes.

ClickHouse 26.11+ gives each insert-backed write tool a programmable response, without a follow-up SELECT.

SQL
ALTER TABLE app.open_incident
MODIFY COMMENT '{
  "title": "Open incident",
  "description": "Create an incident and return its ID.",
  "returning": "SELECT incident_id, opened_at, severity"
}';

-- Generated SQL (illustrative)
INSERT INTO app.open_incident
    (request_id, title, severity)
RETURNING (SELECT incident_id, opened_at, severity)
VALUES ('11111111-1111-4111-8111-111111111111',
        'Ingestion lag', 'critical');
Illustrative legacy QueryResult envelope
{
  "columns": ["incident_id", "opened_at", "severity"],
  "types": ["UUID", "DateTime64(3)", "String"],
  "rows": [
    ["019b0000-0000-7000-8000-000000000001",
     "2026-11-26T11:00:00.000Z", "critical"]
  ],
  "count": 1
}
Do not overstate RETURNING

The response describes inserted blocks after defaults, not necessarily final persisted state or downstream MV output. It stays a write; consume the stream to completion, bound retained response bytes, do not blindly retry ambiguous writes. Verify native driver protocol revision 54495 or use verified HTTP. #207 handles structured output and its schema independently.

10 / typed API

One typed API, multiple consumers.

#207 is an independent P0 feature: derive output schemas where reliable and return real structuredContent, without requiring an MCP App.

Illustrative structuredContent · opt-in object rows
{
  "rows": [{
    "incident_id": "019b0000-0000-7000-8000-000000000001",
    "title": "Ingestion lag",
    "severity": "critical",
    "opened_at": "2026-11-26T11:00:00.000Z"
  }],
  "count": 1
}
Illustrative client-side code
// Programmatic MCP client
const r = await client.callTool({
  name: "list_incidents",
  arguments: {severity: "critical"}
});
if (r.isError) throw Error("Tool failed");
const rows = r.structuredContent.rows;
// Use validated objects; handle truncation.
return rows.map(x => x.incident_id);
Schema and compatibility

Keep positional columns/types/rows/count by default; object rows are opt-in. Infer from trusted view metadata or use validated COMMENT overrides. Preserve large-number precision, nulls, nested types and truthful truncation. No write execution during schema discovery. Code Mode availability in public chat UIs is not assumed.

11 / shared resources

4. Publish one physical application catalog.

Reference deployment: one replicated/versioned table for small application definitions. The connector requires logical interfaces, not this physical schema.

SQL
CREATE TABLE app.mcp_catalog
(
    kind LowCardinality(String),
    id String,
    name String,
    description String DEFAULT '',
    mime_type String DEFAULT 'text/plain',
    content String,
    metadata String DEFAULT '{}',
    revision UInt64
)
ENGINE = ReplicatedReplacingMergeTree(
    '/clickhouse/tables/{shard}/app/mcp_catalog',
    '{replica}',
    revision
)
ORDER BY (kind, id);
ONE PHYSICAL TABLE

Multiple kinds

  • resource: ordinary documents, SKILL.md and references, HTML UI, optional instructions.
  • prompt: static messages and argument/renderer metadata.
  • Optional template and event: approved definitions, not event occurrences.
  • Use ordinary protocol-specific views. No second replicated table for Skills, Apps, Prompts or instructions.
Reference deployment, not a mandatory engine

Use deployment-unique Keeper paths/macros, or ReplacingMergeTree(revision) for a non-replicated deployment. Publishers assign strictly ordered revisions and prevent conflicts; FINAL is not a uniqueness or cross-replica consistency guarantee. Split physical storage if authorization, workload or retention demands it.

12 / logical interfaces

Expose logical views over the catalog.

Core Resources and resource templates are the common foundation for Skills, Apps and application documents.

SQL — logical resource view
CREATE VIEW app.mcp_resources
SQL SECURITY INVOKER
AS
SELECT id AS uri, name, description,
       mime_type, content, metadata
FROM app.mcp_catalog FINAL
WHERE kind = 'resource';
YAML — proposed source
server:
  resources:
    - table: app.mcp_resources
  # optional:
  instructions_resource: app://instructions.md
Storage and access boundary

Respect caller grants, row policies and underlying-table access for invoker views. Reject ambiguous published URIs; serve exact bytes. Keep domain data, event outboxes, subscriptions, checkpoints, jobs and audit logs outside this definition catalog.

14 / prompts

6. Publish explicit workflow entry points.

Prompts are not deprecated. Unlike Skills, they are user-selected workflows that may take arguments and return ordered MCP messages.

SQL
CREATE VIEW app.mcp_prompts
SQL SECURITY INVOKER
AS
SELECT
    id AS name,
    mcp_catalog.name AS title,
    description,
    JSONExtractRaw(metadata, 'arguments') AS arguments,
    content AS messages
FROM app.mcp_catalog FINAL
WHERE kind = 'prompt';

-- Catalog row: kind='prompt'
-- id='monthly_report', revision=1
-- metadata='{"arguments":[{"name":"month",
--   "required":true}]}'
-- content = JSON messages for static prompts
-- Parameterized prompts: approved rendering view
PROTOCOL

Logical prompt view + rendering

  • prompts/list returns visible descriptors and arguments; prompts/get returns ordered messages.
  • No additional replicated prompt table. An approved parameterized view renders messages for a bound month or incident ID; validate the returned protocol shape.
  • Embedded/referenced resources use #202. Optional completion/complete may suggest argument values later.
  • Claude supports user-selected prompts in relevant surfaces; ChatGPT native invocation is unverified. Offer an app entry point or named workflow tool as fallback.
Different jobs, same application

Prompt = start a workflow. Skill = how to perform a workflow. Resource = content. Tool = authorized operation. App = interactive UI. Configurable server instructions (#196) provide concise app-wide guidance, not another authorization layer.

15 / UI gap

7. Add MCP Apps backed by ClickHouse.

#203 supplies the presentation layer over #202 Resources and #207 typed results. Both hosts obtain the UI document through MCP.

ADD TO ALTiNITY MCP

Reuse the resource provider

  • Load HTML from the same app.mcp_resources table or view as skills and documents.
  • Use versioned ui:// URIs and the MIME type text/html;profile=mcp-app.
  • Allow reviewed resource metadata: CSP, permissions and host display settings.
  • Resolve assets with the same effective user and cluster identity.
ADD TO TOOL METADATA

Bind UI; consume the typed API

  • Extend COMMENT JSON with an allowlisted ui binding and presentation metadata. #207 owns output schemas and result formats.
  • Consume #207 structuredContent; the same typed results and text fallback work without a UI.
  • Enforce UI/model visibility, and authorize every tool call from the iframe as usual.
  • Support standard MCP Apps first; feature-detect optional host extensions.

Proposed in #203, depending on #202 and #207. A ui:// URI is a logical MCP resource ID, not an external HTTP URL. The current dynamic registration constructs name/title/description/annotations/inputSchema only, and the result builder emits text blocks.

9. Let users and agents operate the same application.

Bundle the component once, store the bundle in ClickHouse, and run it in a host-managed sandbox.

TypeScript / illustrative SDK flow
// Component source (before bundling):
import { App } from "@modelcontextprotocol/ext-apps";

const app = new App({name: "Incident console",
                     version: "1.0.0"});

app.ontoolresult = (result) => {
  renderIncidentRows(result.structuredContent);
};

await app.connect();

// On an explicit refresh action:
const result = await app.callServerTool({
  name: "list_incidents",
  arguments: {severity: "critical"}

renderIncidentRows(result.structuredContent);
CONTRACT

The UI consumes the same typed API

  • Build with the MCP Apps SDK; inline or bundle scripts/styles into one approved HTML resource.
  • Render untrusted row values as text, not HTML. Do not put database credentials, bearer tokens or signing secrets in the iframe.
  • Use the host bridge for tool calls; do not connect the browser directly to ClickHouse.
  • Consume #207's documented row shape. App state is transient; durable selections, preferences and edits go through authorized named tools.
Portability

Standard MCP Apps first. Keep useful model-readable output when UI is unavailable. Claude-specific app tools can let the model change current UI selection; OpenAI-specific entrypoints and window.openai helpers can enhance host integration, but should not be necessary for the core workflow.

18 / events

10. Turn inserted data into agent-triggering events.

Build an append-only event/outbox projection; route it to subscribed clients via the connector.

SQL
CREATE TABLE app.incident_outbox
(
    event_id UUID,
    event_time DateTime64(3),
    severity String,
    title String
)
ENGINE = MergeTree
ORDER BY (event_time, event_id)
SETTINGS enable_block_number_column = 1,
         enable_block_offset_column = 1;

-- Create an incremental materialized view
-- from open_incident to this outbox.
-- ClickHouse 26.6+ (experimental):
SET enable_streaming_queries = 1;
SELECT _block_number, _block_offset,
       event_id, event_time, severity, title
FROM app.incident_outbox STREAM;
EVENT CONTRACT

Persist the lifecycle in ClickHouse

  • Expose incident.opened with a severity filter and a bounded payload schema.
  • Persist subscriptions, leases, cursors, retry state and dedup keys; the generic dispatcher has no app-specific logic.
  • Use source identity plus stable event IDs; checkpoint only after durable enqueue.
  • Reauthorize long-lived consumers, verify callback signatures/challenges and enforce outbound URL policy.

ClickHouse streaming is experimental and limited to supported sources; use SQL polling for snapshot thresholds and older versions. ChatGPT uses a pre-final webhook profile. Verify its capability keys and webhook-id behavior separately. Claude Events support is unverified; use user-triggered refresh or other approved monitoring paths. Event receipt does not authorize writes.

19 / async work

11. Add long-running jobs and user decisions.

Tasks and Events solve different problems: a task is requested work; an event is something that happened.

P1 · TASKS

Durable job registry

  • Keep approved job definitions in ClickHouse; choose durable job state and ownership storage according to its transactional guarantees.
  • A generic worker claims authorized jobs through a safe coordination mechanism, executes approved SQL and persists results; support cancellation, timeouts and recovery.
  • Expose MCP Tasks when negotiated, with standard lifecycle operations and no session affinity.
  • Fallback: ordinary start_job, get_job, cancel_job tools; return a job ID immediately.
P1 · ELICITATION

Structured human input

  • A tool may need approval, missing parameters or a URL interaction. The host renders a native form from a schema (next slide).
  • Carry signed opaque continuation state or persist pending requests; bind to principal, operation and expiry.
  • Use MCP Elicitation when negotiated. Otherwise expose prepare/confirm operations or a UI form with a validated confirmation token.
  • Never rely on model instructions or tool annotations alone to authorize consequential writes.
Host reality

Claude announced Tasks and Elicitation GA on Nov 24 for eligible individual plans, with organization rollout. OpenAI documents Elicitation; native MCP Tasks was not verified. Implement fallback job tools rather than block the portable experience.

23 / design constraints

Stateless gateway ≠ system with no state.

Durable app state lives in ClickHouse. Some operational mechanisms cannot be wished away.

IDENTITY

Least privilege

  • Separate app roles from operator/DDL publisher roles.
  • Do not trust user-supplied tenant IDs; derive identity from validated credentials.
  • Scope direct resource URI reads, UI tool calls, skill manifests and event subscriptions to principal + cluster.
  • No authenticated fallback to shared DB credentials.
DURABILITY

Correctness boundaries

  • Append-only journal, projections, event IDs, durable checkpoints and recovery.
  • Coordinate worker leases and deduplication; ClickHouse sorting keys are not unique constraints or distributed locks.
  • Frequent small inserts and mutable state deserve a workload-specific design. For strict task claiming, uniqueness or transactional state, use an appropriate transactional dependency.
TRUST

Code and content

  • Treat COMMENT metadata, skill content and HTML as executable-influence surfaces; only trusted publishers may modify them.
  • Version/review HTML assets; restrict CSP and network access. Validate schemas, file sizes and callbacks.
  • Record audit IDs, status and counts without logging tokens, full secrets or sensitive content.
Where the thin-proxy principle stops

A generic worker or coordination/queue service may be necessary for reliable webhook retries, async jobs or outbound effects. It can keep domain decisions in SQL and store authoritative state in ClickHouse, but cannot promise atomic distributed leases, exactly-once delivery or safe transaction semantics just because the adapter is stateless.

24 / backend fit

Choose ClickHouse for the right workload.

The application platform targets data-intensive analysis and append-oriented workflows, not arbitrary OLTP or a general-purpose coordination service.

STRONG FIT

ClickHouse

  • Business analytics and interactive dashboards.
  • Infrastructure diagnostics and observability.
  • Large historical knowledge and retrieval workloads.
  • Batched observations, event history and low-frequency append commands.
TRANSACTIONAL FIT

PostgreSQL or equivalent

  • Frequently updated working memory and operational facts.
  • Atomic task claims, locks, uniqueness and idempotency.
  • Pending approvals, transactional queues and authoritative mutable state.
  • Cross-row invariants, inventory or financial operations requiring transactional guarantees.
Two independent limitations

Single-row insert frequency affects part creation, merges and replication; async inserts can batch data. That does not create uniqueness, cross-row transactions or safe exclusive task ownership. Keep the incident example a low-frequency analytical workflow. Do not build a multi-agent coordination reference app.

27 / conclusion

The analytical application lives in ClickHouse.

Altinity MCP is the reusable gateway for data-intensive, database-defined applications.

Application operations

Views → reads
Tables → commands
RETURNING → receipts
Typed outputs → composable API
Events → triggers

Shared resources and workflows

Resources → content
Skills → expertise
Apps → interactive UI
Prompts → workflow entry points

Recommended decision

Follow roadmap #205: deliver static instructions (#196), typed outputs (#207) and shared Resources (#202) as independent foundations. Build native Skills and MCP Apps over them. One definition catalog where practical; ordinary resource/prompt views; separate runtime state. Keep Code Mode client-side and use transactional storage where required.

The architecture is strongest for analytical and append-oriented workflows. It is not a general replacement for a transactional application server, an identity provider, or a durable job runner where the application's requirements demand those capabilities.
